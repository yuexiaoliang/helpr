# 01 启动诊断与内部宿主修正

2026-10-15，用户解锁后，build 9 的启动 23 仍在 ready 前以 1 结束，网站回执为空，全部已见自有进程结束。按上一轮停止条件，保留失败包并恢复原 build 7，核对原 hash 与 deep／strict 签名；恢复本身累计为安装 7，没有启动应用或改动用户资料。

现有诊断只显示控制进程结束，不能区分启动资格检查、资源加载或原生入口。先修复这条反馈路径，再决定产品修正，避免继续按猜测替换应用。

## 已准备的源码

- main 只报告固定阶段和枚举错误码，不发送原始异常、路径、参数或凭据；最多等待 100ms 冲出回执。
- 原生监督在自有 fd 6 上保留实际子退出码／信号。宿主不继承 fd 6，控制者按行处理分片。
- 控制者在进程 exit 时立即撤销能力和结束工作者；以 100ms 总上限等待通道排空、日志关闭及验证回执，避免退出码仍被丢失。
- 真实 Node／原生监督的退出 64 回归先失败、修后通过；两轴复核指出的关闭时序已修正。这不证明 Electron 或 CUA 已修好。

## 单次运行边界

仅新增 1 次构建，在独立构建目录运行 1 次空资料启动诊断。已有启动上限 24 不增加；累计构建上限 10、安装仍 7、启动仍 24、故障仍 4、必要清理仍 10。原计数和失败全部保留，模型和远程业务写入均 0。

入口：`node scripts/validate-workspace-ui.mjs --build 10 --built --startup-only`。不替换已恢复的安装，不建立测试网站、不创建任务、不读取原会话、不测试 CUA 或真人输入。ready 等待最多 15 秒；若意外正常启动，仅经既有公开退出入口结束，退出等待最多 5 秒，必要清理最多 3 秒。只有此空资料诊断模式不要求可见桌面；正常 UI 走查仍须通过锁屏与受保护输入预检。

保存固定错误码、实际退出状态及所有已见进程的结束结果。一次结束后不追加同类尝试；先依据具体结果提出下一项源码修正。若仍没有阶段或错误码，记录该未知，不能宣称问题已定位。

## 单次诊断结果与下一项修正

build 10 仅在构建目录启动 24，没有替换安装版。原生回执为 signal 5，未生成 JS 错误码；全部已见进程结束。独立系统崩溃报告与本机同 UUID 的 framework 静态反汇编确认：子进程在 `electron_main_delegate_mac.mm` 的“Unable to find helper app”检查结束，宿主随后在 `gpu_data_manager_impl_private.cc` 的“GPU process isn't usable”路径结束。没有从裁剪后的 DNS／TLS 符号名推定原因；官方符号包下载超时，未用不完整资料作为函数映射。

据此移除跨 bundle 共享 helper 的布局，采用 builder 产物的完整独立主应用结构：内部宿主有自己的 framework、四种 helper 和同一应用 ASAR，保留原始相对 RPATH，明确主应用标记与内部 helper 身份。复制时保留 framework 相对符号链接，系统支持时采用文件克隆；逻辑包体会增加，具体磁盘和资源代价以实际包测量。控制职责、数据位置与已确认界面不变，不修改 runtime 二进制搜索路径。

新增只读包核对 `scripts/validate-host-package.mjs`；已在失败 build 10 上报 `HOST_MAIN_BUNDLE_REQUIRED`。后续打包须通过主入口、四种 helper、ASAR 一致、framework 留在本 bundle、fuses 一致及 deep／strict 签名检查，才能启动。

下一批最多 1 构建、3 启动：先在构建目录检查空工作区和 CUA 读取；通过后才安装并做双任务／冷重开。最多 1 次新安装及必要时 1 次回退，累计上限构建 11、安装 9、启动 27；故障 4／必要清理 10 不变。安装版当前仍为 build 7。每批最多 30 分钟，系统授权或再次出现原生失败即保存证据停止，不继续试包；模型与远程业务写入仍 0。没有把修正后的布局断言算作实际窗口或凭据通过。
