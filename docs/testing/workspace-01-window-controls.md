# 01 macOS 原生窗口按钮可见性

## 范围与已有失败

属于事项 01 已确认的基础工作区，不改标签栏设计或关闭主窗口只收起的约定。用户在 build 11 真人核对中看不到红色关闭按钮；候选 13／启动 35 的自身窗口截图仍看不到三色按钮，但 AX 有关闭、全屏、最小化项。真实可见性反馈入口为 CUA 的 `getScreenshot()`，再根据截图确认左上角三色按钮；AX 存在不足以捕获该缺陷，不能用它作通过断言。35 的焦点门控通过与本问题分开，见[原证据](evidence/workspace-01/focus-green-35.json)。

初步已排除窗口整体越界和全屏：32 的固定只读 inspect 表明 bounds 在工作区内且非全屏，按钮位置为 12／18；35 仍是同一布局的普通窗口。该历史几何不替代新候选的视觉检查。

## 假设与单变量候选

1. 标题栏按钮容器在构建／显示过程中没有保持可见。预测：窗口 show 时显式恢复系统按钮可见性、重绘容器，可恢复三色按钮；不改 CSS、位置或内容视图结构。
2. 自定义按钮位置被 AppKit 重新布局或裁切。预测：仅恢复可见性无效，需要另行比较系统默认位置；本批不改位置。
3. 多个原生内容视图遮住标题栏区域。预测：仅恢复可见性无效，按钮像素依然不可见；下一轮应隔离视图层级，不能在当前候选同时调整布局。
4. 工具截图没有呈现原生控件。历史真人看不到的结果使它不能作为唯一解释，但新截图和真实点击仍须分别记录，不以 API 设值替代可见性。

同版 Electron 44.7.2 的 [NativeWindowMac::SetWindowButtonVisibility](https://github.com/electron/electron/blob/v44.7.2/shell/browser/native_window_mac.mm#L1409)会重新绘制按钮容器、取消其隐藏并设置三个标准按钮 hidden 值；构造时 hiddenInset 已显示各按钮，但不等于后续容器必然保持可见。[官方标题栏说明](https://www.electronjs.org/docs/latest/tutorial/custom-title-bar)亦说明该 API 可强制显示／隐藏原生按钮。这仅是可检验机制依据，不断言本机根因已经定位。

候选只在非全屏窗口 show 时调用 `setWindowButtonVisibility(true)`，覆盖初次展示及已有窗口从收起返回；不调整坐标、尺寸、frame、HTML 或 CSS。全屏时跳过，继续交给系统原有全屏处理。不会添加自画红点或新关闭入口，也不改已有 close 事件的收起和退出规则。

正确回归边界是实际 macOS 原生窗口及真实可见性／点击。单个 jsdom、伪造 Electron setter 或源码字符串检查不能证明按钮可见，不新增这类假回归；现有源码检查和真实原生验证保持各自范围。

## 有界准备与待执行核对

当前用量为构建 13／安装 8／启动 35／故障 4／清理 11。只新增一次候选构建 14，累计上限构建 14／安装 10／启动 36／故障 4／清理 12；其它上限不变，不构建第二候选，不清零历史计数。原候选 13 的已通过焦点路径保留，当前安装 11 不动。

先在后台完成源码检查、候选和离线包验证。需要桌面前，提供现成候选，再等用户明确短暂让出输入；此前的前台让出已结束，不从“继续”推定可抢桌面。原生轮最多启动 36 一次、3 分钟，独立超时 abort 沿用既有入口，至多一次必要清理。若按钮不可见、工具／系统授权／受保护输入受阻、用户状态变化或时限到，保存并结束，不同类重开或添加修正。

若三色按钮可见，只点击真实可见的红色按钮确认窗口收起，再使用已批准菜单栏／Dock 返回路径核对原任务和对话，最后真实 UI 正常退出；工具无法可靠点 Dock 时请用户完成该单步，不能由 show 命令冒充 Dock。必要时只做已获准卡片 Down／Esc／Tab 检查，网站仅自有本机虚构页。该轮不安装；安装后首次／冷重开单独准备，不越过现有上限。

本批模型调用、远程业务写入和故障注入均 0，不更改系统权限、证书信任或安全设置。候选未实际通过可见性和点击前，不称修复完成或勾选事项 01。

## build 14／启动 36 的实际结果

后台完整 `pnpm check` 通过：5 文件 12 项、类型／lint／格式及 187 文件语法、既有归档检查；没有新增真实模型请求。标准完整内部 bundle／四种 helper／同 ASAR／fuses／deep strict 签名通过。两轴源码复核均 0 项实质问题。原候选 13 在忽略目录保留，当前安装 11 不动。

用户明确“现在可以，开始核对”后，仅启动 36。原记录基线比较通过；自身窗口的两次真实 CUA 截图已显示左上角红、黄、绿三个原生按钮，初次可见性通过。该轮只验证本次窗口显示的恢复，不倒推原隐藏由哪个内部标志造成，也没有覆盖其它生命周期。

按 AX 关闭项执行一次点击后，后续 AX 仍显示窗口；另根据截图尝试一次坐标点击后也仍显示，坐标单位没有独立核对，不以此判定产品 close 回调失效。之后再按当前 AX 关闭项点击，按预定流程请用户只看窗口是否收起并点击 Dock 返回。用户答复“应用已经不在了”；具体观察与时限的相对时刻未建立，不能据此称原生红按钮导致退出、崩溃或 Dock 返回通过，也不能将观察接口再次看到窗口解释为确定的重新显示机制。

独立计时器在 180 秒写入 abort，本轮 180.431 秒结束。验证脚本明确记录 `CUA_UI_ROUND_ABORTED`、SIGKILL，并使用清理 12；15 个已见自有进程全部结束，服务结束。这是有界程序的超时中止，不能称正常退出通过。已告知用户无需再找窗口、可恢复使用电脑；没有继续启动、安装或修正构建。

累计构建 14／安装 8／启动 36／故障 4／清理 12，现行上限 14／10／36／4／12；模型和远程业务写入 0。按钮初始显示已恢复，真实红按钮收起／Dock 返回／正常退出尚未完成；候选 14 未安装、当前安装仍 build 11，hash 未变。35 的焦点通过仍仅属于候选 13，不抵算 14 已组合复验。后续先准备明确的人工两步与超时阶段记录，再另列有界验证；不从上次前台让出推定可继续操作桌面。见[实际限定证据](evidence/workspace-01/window-controls-36.json)。
