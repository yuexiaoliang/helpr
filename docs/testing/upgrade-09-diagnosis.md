## 已查明的退出缺陷

普通 `quit` 曾用 `upgrades.held()` 拒绝退出。该函数表示自动派发需要暂停；新版启动后进入 `checking`，即使检查尚未开始、没有保存操作进行中，也会返回true。因此103的正常退出直接得到 `UPGRADE_PENDING`，验证器转入信号清理。这与用户已确认的“可靠保存后可明确退出、重开先核对”不一致。

将controller中原有quit协调分支原样提取为真实调用函数后，以下检查在修正前得到 `UPGRADE_PENDING`，总耗时826ms，无Electron启动：

```sh
pnpm exec vitest run tests/workspace/upgrade.test.ts -t '升级后尚待检查时普通退出'
```

修正使用独立的 `UpgradeService.canExit()`：初始化完成且没有正在进行的准备／检查时，可以走既有可靠保存和退出；不清除升级记录、不改成检查通过、不释放自动执行屏障。普通退出仍采用原有“放弃网页编辑并退出”确认和保存检查，不代替用户保存网站内容。初始化或异步准备／检查进行中继续拒绝；记录、执行或备份尚未可靠保存也继续拒绝。专用的升级退出按钮仍要求当前准备、指纹和备份有效。

4项回归使用真实UpgradeService、临时SQLite与controller实际quit协调函数，覆盖：待检查退出并重开仍暂停、失败后退出不改变原失败／备份、检查进行中及保存未完成拒绝、退出保存失败保持原记录。Electron接口隔离，不能将这些检查记为实际进程退出验收。
