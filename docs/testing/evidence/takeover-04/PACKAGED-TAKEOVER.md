## 保留的客户端失败与写锁样本

第一轮（累计启动 56）前三组接管通过后，临时客户端错误地给严格的 `reload` 命令附加 `requestId`，得到 `INVALID_REQUEST`，刷新没有执行。夹具按失败规则正常退出，退出码 0、无自有残留。随后只补未通过的页面变化，前三组没有重做。

同轮曾有一次展示脚本把结果元数据当成含有 `text` 的正文而报错；此前的行为断言已经通过，改用所属任务公开 AX 观察确认文字，不重新执行网页动作。第二轮客户端短暂读到尚未写完的控制回执 JSON，随后读取完整回执续做，没有重发刷新。永久夹具的 JSON 发布改为先写临时文件再重命名，后续消费者不会看到半份回执；本轮运行中的旧写入器没有被替换，不冒充该修正已完成新的实包运行。

第二轮（累计启动 57）最后安排一次约 2.5 秒的外部 SQLite 写锁后回滚，不读取或修改业务行，不终止记录进程。实际公开“继续”约 103 ms 后即返回 `RECORDS_UNAVAILABLE`；键盘收件约在持锁开始 10.5 秒后，已经晚于释放。F 没有新增网页效果。**此样本没有形成所计划的慢保存与原生输入重叠，不能作为“输入先于保存完成”的通过证据。** 它仅增加一项记录不可用时未放行 F 的受控观察。

记录失败后本轮停止。公开退出未在 45 秒内完成，不能记录正常退出通过；临时现场使用预留的一次自有清理，分别核对同一候选 PID 后先 `SIGTERM`、仍在后 `SIGKILL`。独立全进程查询确认无该候选残留，未处理其它应用或系统授权进程。原临时资料及记录失败保留；没有以换样本或重启把此竞争判为通过。
