# 01 任务卡片键盘焦点诊断

## 已取得的失败信号

build 11／启动 28，真实 CUA 操作：从任务 B 的对话保存草稿，点击 A 标签，按 Down。卡片显示 A 的目标和最近动态，但 AX 焦点为窗口容器；按 Esc 后卡片仍在，按 Tab 后焦点落回 A 标签。之后仅用已显示的卡片关闭按钮收起，准备人工输入，不重复上述试验。

这是实际多 WebContentsView 的键盘归属失败；单个 jsdom renderer 的 `.focus()` 检查无法覆盖原生视图的第一响应者，不用这种测试冒充回归。已有启动 26 的 Down／Esc 结果和焦点未知保留，不覆盖为全部失败。

可重复反馈入口：CUA 绑定已安装内部宿主，取得完整 AX 后从实际 A 标签操作 Down → AX → Esc → AX → Tab → AX。成功要求 Down 后卡片取得焦点，Esc 关闭并回到原标签，下一次 Tab 进入该标签的收起按钮。不能只检查卡片存在或消失。

## 待逐项检验的假设（按优先级）

1. 选择任务的保存回执晚于卡片取得焦点；每次 state 更新都移除再添加原生 overlay，使第一响应者丢失。预测：没有后续 state 更新时正常；保留 overlay 原生挂载后同样的选择／打开顺序仍保持卡片焦点。
2. 鼠标悬停计时器在键盘 Down 后再次发送不带 focus 的 preview。预测：鼠标离开标签后仅键盘打开可避免丢失；取消先前悬停计时可消除覆盖，但仍须核对 state 更新。
3. 原生 view 聚焦和 renderer 内 DOM 聚焦的异步顺序不受约束，关闭时隐藏 overlay 后才判断旧焦点也可能错过返回。预测：显式限定面板版本及聚焦目标的请求／回执可使打开与关闭均稳定；如果只改挂载仍失败再核对这一项。

先完成当前安装包独立的中文输入与登录冷重开证据，期间不修改运行包或抢走人工输入焦点。后续只在既有已确认键盘行为内修正；每次原生验证仍需另列有界构建／启动计划，保留所有失败。

先用原 build 11 的同资料记录恢复完成可断言的 CUA 失败循环并正常退出；再只修正已定位的多视图挂载更新，不改变 UI 设计或对话行为。完整安装候选不通过同一路径就不替换安装版。需要系统授权、崩溃、CUA 传输阻碍或修后同类失败时保留证据并停止；不把预期的旧包焦点红例当作修后通过。剩余清理最多 1 次，不无限追加。

用户回报看不到红色关闭按钮，当前只能确认 AX 存在该原生按钮，实际位置与可见性未定位。候选只增加受限 inspect 返回自身窗口 bounds、contentBounds、全屏状态与原生按钮位置，用于区分窗口越界与标题栏布局；不先调整外观，不以存在 AX 按钮代替可见性验收。

## 旧包最小反馈与候选源码

启动 30，首次快速选择未失败；同一窗口下一次快速选择在回执门控前已丢失焦点，该次不能隔离网页完成因素。改为先完成标签选择、打开卡片并断言 AX 焦点在卡片，再释放本机 HTTP 响应。实际第二个断言报 `CARD_FOCUS_LOST_ON_PAGE_RECEIPT`，AX 焦点从卡片转到网站 document。另一次 Esc 关闭后，焦点转到隐藏 B 对话，原标签并未恢复。两条均为真实多视图原生反馈，不是 jsdom 推导。

候选只改变对应两条路径：只在新增任务视图时提高 overlay／toast 层级，普通 state 回执不再 remove／add；关闭前记录 overlay 是否取得焦点，隐藏后按原归属返回 chrome，避免隐藏动作先改变焦点再判断。现成 [View API](https://www.electronjs.org/docs/latest/api/view#viewaddchildviewview-index) 支持重新添加已有子视图来调整层级，无需手动移除。来源只是 API 依据，真正焦点行为仍由候选同一路径确认。

本次正确回归边界是实际 Electron 窗口和 CUA 原生键盘；没有新增只在单个 React DOM 中 `.focus()` 的测试冒充原生回归。现有输入法／草稿测试保持；候选必须重跑门控反馈及 Esc → Tab 次序，再决定是否安装。启动 30 的记录恢复／退出脚本自身通过与焦点红例分开记录；该轮额外门控服务器属于单独本机诊断，不提供会话证据。
