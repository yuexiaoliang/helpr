# 执行与调度设计建议

状态：首版最多两项独立任务并行的产品范围已确认，浏览器组合与持久化协议已分别确定，产品尚未实现。本文保留早期职责与场景建议；具体选择以[确定浏览器承载与流程执行组合](../../.scratch/helpr-first-release/issues/07-browser-runtime-decision.md#answer)和[确定执行记录、流程更新与定时恢复的约定](../../.scratch/helpr-first-release/issues/10-durable-execution-contract.md#answer)为准，不能把方案或单项实验当作完整产品已经验收。

## 已确认的约束

- 首版最多两项独立任务同时自动推进，首次 AI 探索和已学流程复用均支持；系统安排执行，超出容量或可能互相影响的任务排队。
- 一次委托中的多个独立平台任务各有标签页，相关标签页归入一个任务组。
- 每个任务独立会话、独立预览确认、独立处理执行与结果；任务组用于整理标签页，不设组级会话。
- 用户直接操作真实网页时接管，明确说“继续”后按当前页面状态恢复；仅查看或切换标签页不接管。
- 定时触发时新建类似浏览器的任务标签页，不切换当前页；需要参与时提供可操作的提示。
- 参与请求可以全局提醒；用户可直接操作提醒中的输入组件，回答归入对应任务。标签页同时提供简洁明确的进度。
- 用户首次在真实网页登录，后续复用登录状态。
- 接管、停止、内容确认与结果各自独立，不受相关影响的任务继续；用户无需配置并发机制。
- 停止后收到用户新的明确“继续”指令，先核对已有结果再续做剩余工作；已经完成就告知结果，不重发。查看历史、重新登录和程序重启不替代这条指令。
- AI 根据前次执行的实际阻碍判断对后续执行的影响，并与用户约定处理方式：单篇内容问题通常只影响本次，失效登录会影响依赖该登录状态的后续执行。
- 意外中断后，对原本自动执行的任务先核对实际状态，再尽量继续；等待参与和已停止的任务保持原状态。
- 已结束任务可直接关闭并保留历史；未完成任务的关闭提示提供收起与停止。收起保持原执行状态，明确的停止指令直接生效，已有定时计划保持有效。

## 设计建议

每次执行独立持有自己的目标、素材、网页关联、进度、待回答的问题和结果。是否可以开始自动操作，由调度统一安排；用户当前选中的标签页只决定看到什么。

任务组用于组织相关任务，调度安排仍归到具体执行。共用同一素材的多个平台任务分别确认各自内容；某个任务遇到问题时按该任务的实际状态处理。任务之间如确有目标或数据依赖，需要明确记录该关系，不能仅凭它们同属一个组推断依赖。

例如，A 等待用户确认内容时保留现场，B 可以继续执行。用户在 A 的提示中完成确认后，A 回到可执行队列；有空余容量且没有冲突时，A 可以与 B 并行，容量已满时继续排队。任务恢复前需要重新核对网页及素材状态，不能假定等待期间没有变化。

用户可见行为按已确认需求验收；下列早期 Module 职责建议中，尚未由已确定协议收敛的内部细节继续留给工程设计，不代表用户已经逐项指定实现机制。

已确定的持久化协议由单一拥有者统一保存关联记录，执行固定流程、素材和内容版本；接受回复、领取工作、预留动作、登记完成及采用候选分别约束本地原子变化。网页效果在事务外，恢复需核对实际结果，旧执行或旧参与回复不能覆盖新意图。待确认、停止和结果不明的素材工作保持原归属，不由下一轮定时触发重新创建；具体事实、Interface 和待验证范围见上述决定。

### 职责与 Interface

| Module | 对外的 Interface 与保证 | 内部承担的复杂性 |
| --- | --- | --- |
| 单次执行 | 接收所属任务的用户回答、继续、停止和目标修正；提供该次执行的状态与结果 | 保存现场、关联网页、处理人工接管、判断恢复位置、丢弃过时的执行结果 |
| 调度 | 接收可执行的工作，在并发数量和资源允许时安排；首版最多两项独立任务同时自动执行 | 排队、等待时让出执行机会、恢复后重新排队、避免互相影响的工作同时操作共享资源 |
| 工作区 | 显示对应任务的网页、独立对话和标签页进度；通过全局提醒接收对参与请求的回答，并交给所属执行 | 标签页分组、前后台显示、提醒内操作与提示跳转，以及真实网页与浮窗的呈现 |

这三个 Module 的 Interface 不暴露特定网站、栏目或 Excel 业务规则。实际代码如何组织、是否需要更多内部划分，留待最小验证后决定；本设计不要求为每个职责新建独立进程。

### 等待、接管与恢复

- 等待用户参与时，保留对应执行的网页、素材和问题。该执行确认不再继续派发网页动作后，调度可以安排不受该阻碍影响的任务；等待登录等共同前提时，同时识别依赖该前提的其它执行。
- 提示中的操作必须关联到发出提示的执行。用户正在看 B 时回答 A 的问题，不能把回答应用到 B。
- 同一参与请求可以在提醒和任务会话中呈现，处理后需要同步更新各处状态。过期提示或重复提交不能触发额外的网页动作。
- 接管 A 时，让出的是 A 的网页操作。其他执行是否能运行，由各自状态与资源条件决定。
- 用户说“继续”或回答完问题后，执行仍需满足原有内容确认与发布约定；补充信息不能被自动扩大解释为同意新的发布内容。
- 停止后明确继续，保留已经产生的结果及原有约定，核对后只做剩余工作；结果尚不确定时不能自动重试。停止前失效的参与请求与旧处理结果仍然失效，不能随新的继续指令重新生效。
- 旧动作、延迟模型回复或过时的用户提示，不能在执行停止、目标修正或重新开始后擅自恢复网页操作。

### 按实际阻碍安排后续执行

AI 需要根据当前页面、素材、执行记录和用户已有约定，判断阻碍影响本次内容、某个登录状态，还是其他共享条件；调度依照这些已确定的条件安排执行。相同的“等待用户”显示状态可能具有不同的实际影响，不能只看一个状态值就全部放行或全部阻塞。

例如，昨日文章仍待确认时，今日素材可以按约定形成新的执行；同一网站账号已退出登录时，依赖这份登录状态的任务等待，使用其他有效会话的任务仍可执行。

设计建议是让同一登录问题复用一个处理入口，并在相关任务中显示原因，减少重复登录提醒。登录完成后分别核对受影响任务能否继续；它们原有的内容确认、停止状态和发布约定仍有效。这种共享前提恢复不等于同时批准多个任务的发布内容。

共同阻碍解除后，积压工作按已有约定处理；没有覆盖该情况的约定时，AI 根据任务时效和目标提出具体建议，请用户确定。用户不需要选择工程上的阻碍类别。

### 意外中断后的恢复核对

恢复依据是记录中的执行状态与网站实际结果。中断前正在自动执行的工作，在确认进度和继续所需条件后恢复；已产生完整结果的工作据实结束；无法确定是否已经提交的工作提出参与请求。

等待用户的执行保留问题和已有回答，用户已停止的执行在收到新的明确“继续”指令前保持停止。恢复时还要重新关联正确网页，并避免旧进程遗留结果或重复触发再次派发同一工作。

标签页收起保持原执行状态；具体关闭交互已确认，见 [任务标签页关闭交互](task-tab-close.md)。

### 并行执行需要保持的条件

不能用一个全局“当前网页”或“正在等待用户”的变量代表所有执行。动作、模型响应、人工输入和结果都必须归属于具体执行，界面选中状态不能改变这种归属。

登录状态可以复用，但复用登录不等于共用正在填写的网页。独立任务应能保留各自的页面现场；同一网页的实际操作权必须明确。改变共享登录会话、切换账号等行为可能影响其他任务，需要重新核对受影响的执行。

并行执行时，必须检验页面关联、共享会话干扰和目标操作冲突。网页或资源是否会互相影响，应根据实际能力与观察判断；本轮不假定系统已经能识别任意网站的业务冲突。

首版采用本机执行范围。通过相同的执行与调度 Interface 验证等待、恢复和停止，并在两项独立任务同时运行时核对这些行为；单项路径可以用于调试，交付须包含实际并行的验证。

## 首版并行的范围与交付条件

状态：用户已确认本节中的并行范围与独立控制要求。下述场景用于落实要求，具体资源判断与协调机制仍需设计和验证。

浏览器多页面操作已有原语与受控实验依据，所选完整组合的业务并发、人工接管与恢复仍需共同验收。早期资料与限制见 [首版并行可行性调查](../research/parallel-execution-feasibility.md)，后续运行事实以技术决策地图所索引的各项报告为准。

首版以最多两个独立任务同时自动推进作为初始范围，超出容量的任务排队。两项执行要能在同一段时间分别持续完成网页工作，不能只展示两个“进行中”的标签页，或把一项等待、一项运行当作并行通过。首次 AI 探索与程序复用均应覆盖，模型调用额度和计算资源由系统内部调度。

两项并行是已确认的首版交付范围，机器容量与响应表现尚待实测，并不表示两个任务耗时必然减半。等待参与的执行保留现场，其持有的共享条件能否释放需要核对；是否占用自动执行容量由调度处理，用户不需要选择并发模式。

### 对用户的行为

| 情况 | 对应行为 |
| --- | --- |
| 两个独立任务具备执行条件 | 在各自真实网页上同时推进，不切换用户当前标签页 |
| 用户接管、停止或回答 A | 只作用于 A；不受相关影响的 B 继续执行 |
| A 等待内容确认 | 保留 A 的内容与页面；其它符合条件的任务可以使用执行机会 |
| 两项工作需要操作同一个网页或可能修改同一份记录 | 系统安排先后次序；涉及目标冲突而无法决定时，才向用户询问所需结果 |
| 同一登录状态失效或被手动切换 | 重新核对依赖它的任务，受影响的工作等待；不扩大为所有任务停止 |
| 系统无法判断共享操作是否互相影响 | 保守安排相关任务串行，并用简短状态说明等待原因 |

不能仅凭“网站不同”或“标签页不同”就认定任务完全独立。首版应从明确独立的页面与登录条件建立证据；同一账号下的任务若缺少可靠的相互影响判断，先保守串行。无须为此在源码中添加 WordPress 等网站的专用并发规则，相关资源关系来自实际执行上下文与运行时流程。

### 必须增加的实现与验收工作

- **明确页面归属：**每个动作、观察、模型响应、弹窗、上传与下载都绑定所属执行的实际页面，不用一个全局“当前标签页”隐式决定操作对象。需要系统级焦点或原生交互的步骤单独协调。
- **隔离参与和停止：**在 A、B 都实际运行时接管或停止 A，检查 A 的延迟回复和后续动作不再执行，B 的页面与进度不被误改；从全局提醒处理 A 也要验证相同归属。
- **核对共享条件：**分别验证不同会话、共享登录、同一网页、同一后台记录以及账号切换。浏览器存储隔离不能替代对目标网站结果的核对。
- **隔离素材和产出：**验证同名文件、共用源素材、不同上传及下载结果不会串用；同一素材被两个平台按意图使用，不能被错误地全局去重。
- **处理流程更新：**两个任务同时复用或修复同一流程时，各次执行的已确定步骤不被另一项的更新突然改写；核对成功的修复也不能简单相互覆盖。具体版本机制后续设计。
- **并行中断恢复：**模拟两项任务在不同进度中断，重启后分别核对实际结果，避免漏做、重复发布或恢复用户已停止的执行。
- **测量资源表现：**在目标机器和实际模型 API 上记录响应、页面运行与并发限制，检查后台页面仍能观察和操作；不以单页实验代替并行证明。

页面归属、双页操作、独立停止和人工接管的受控证据已支持承载方式选择，仍需在完整产品中覆盖此处的共享条件和恢复要求。单项路径通过不能代替并行交付验收，交付条件见 [首版验收范围](acceptance-outline.md)。

## 建议验证的场景

以下是落实已确认要求的具体验证建议，尚未执行。首版必须通过两项独立任务并行及控制、共享登录与恢复验证；具体实验步骤仍可在工程设计中调整。

| 场景 | 应观察的行为 |
| --- | --- |
| A 等待内容确认，B 已排队 | A 的页面与问题保留，B 获得执行机会；A 不再自行操作网页 |
| B 执行时用户回答 A | 回答只进入 A；A 回到队列，B 不被错误中断 |
| 用户在全局提醒中处理 A，无需切换当前标签页 | 回答只作用于 A 的对应参与请求，A 的会话和标签页状态同步反映结果 |
| 用户已在提醒中回答，又操作会话里的同一个旧问题 | 原参与请求只处理一次，不重复确认内容或重复派发网页操作 |
| 用户在不同任务标签页之间切换 | 只改变显示；任务不会因为获得或失去可见焦点而自行接管、恢复或停止 |
| A 被人工接管，B 的状态发生变化 | A 的人工页面保持归属，B 的进度或提示不会落到 A |
| A 已停止，但旧模型响应随后到达 | 不再向 A 派发后续操作，也不会误操作 B |
| A 停止后用户明确说“继续” | 先核对已有结果再续做剩余工作；已完成就告知结果，结果不明不重发；旧回复与旧处理结果仍不生效 |
| A 重新登录，B 使用同一网站会话 | 对 B 的影响被识别并重新核对，不把已有登录状态当作永久有效 |
| 昨日文章待确认，今日定时到点 | 根据实际阻碍和已有约定决定今日执行；昨日待确认内容不被替换或误当作已批准 |
| 登录失效期间同一计划多次触发 | 依赖该登录状态的工作等待，并复用处理入口；无关任务仍可执行，积压安排遵循用户约定 |
| 提交请求发出后程序意外退出 | 恢复时核对网站结果，已完成的操作不重复提交；无法确定时明确请求用户参与 |
| 程序重启时有待确认、人工接管和已停止的执行 | 保持各自原有状态，自动恢复机制不替代用户的确认或继续指令 |
| 两项独立任务实际同时推进 | 网页、素材、用户回答与结果互不串用，记录能够证明实际并行；需要共享同一网页的操作仍有明确控制权 |

人工输入识别和浏览器连接仍存在技术验证项，参见 [可见网页工作区调查](../research/visible-browser-workspace.md)。本文记录了按实际阻碍处理后续触发的原则；积压安排需要按具体任务与用户约定，不能由工程实现擅自设为全部补做或全部跳过。
