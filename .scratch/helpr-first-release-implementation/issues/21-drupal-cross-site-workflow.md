# 21: 在 Drupal 学习并完成同样的委托

Status: ready-for-agent
Blocked by: 15
Spec: [首版实现规格](../../helpr-first-release/spec.md)
Index: [实现事项总览](../README.md)
User stories: 7–10、14、18

**What to build:** 同一 helpr 产品在另一套结构不同的真实后台完成附件任务，并能更换输入使用运行时形成的新做法。

## 前置交付与范围

采用已准备的 Drupal 测试后台，验证通用能力跨网站。允许增加有证据的通用原语或协议覆盖，但不能增加 Drupal 专用业务分支、维护者选择器或预填流程。

前置事项：[15 换输入与冷启动流程复用](15-parameterized-and-cold-workflow-reuse.md)。

## Acceptance criteria

- [ ] 使用与 WordPress 路径相同的产品代码，从未预置该业务流程的独立资料区开始，由实际观察形成任务做法。
- [ ] 自然语言委托、固定素材、目标和有效确认／约定经过同一协调与执行入口，真实上传、发布和结果可核对。
- [ ] 后续更换素材或输入可使用产品学得流程，任务、确认、输入和结果不串用；使用新流程不继承另一任务的发布权限。
- [ ] 独立核对 Drupal 真实目标、状态和下载字节，保留多余结果、异常与失败；后台预检或手工跑通不能替代产品证据。
- [ ] 需要新通用能力时遵守已归属页面、frame、session 和执行资格，未支持能力保持拒绝；不能恢复裸端口或授予任意控制作为捷径。
- [ ] 通用修订回归已有 WordPress 行为与受影响的控制／恢复检查，两个站点不因新分支产生不一致的停止和资料关系。
- [ ] 新流程及恢复依据保存并进入冷重开、备份和版本检查；不依赖维护者事后补目标或字段位置。
- [ ] 为五项业务的跨后台场景提供不同输入的真实证据；23 在固定交付候选按每场景两次门槛统一复验，早期证据不自动抵算。

## 验证方式

从正常用户委托入口运行已授权测试后台，以站点记录和下载内容作独立核验。跨平台任务组和三种并行组合在 23 一并复验，不能把两个单任务成功直接视作并行成功。

遵循[总览中的跨事项完成约定](../README.md#跨事项完成约定)，从正式产品公开入口验证并保留独立证据；不把旧实验通过当作本项完成。真实运行沿用具体案例的有效授权与累计消耗上限，本事项的发布本身不启动新实验。
