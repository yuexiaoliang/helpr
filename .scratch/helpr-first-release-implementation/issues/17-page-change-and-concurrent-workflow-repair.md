**What to build:** 网页变化后产品重新观察，在原约定内修复、核对、保存新做法并告知；冷启动可复用修复版，两项任务同时修复同一旧流程也不会丢掉彼此成果。

## 前置交付与范围

基于实际学得流程、真实恢复规则和资源协调完成变化修复。不能通过降低成功条件、改目标或重复未知提交来使修复通过。

前置事项：[14 提交中断后的真实网站结果核对](14-recover-real-publication-outcomes.md)；[15 换输入与冷启动流程复用](15-parameterized-and-cold-workflow-reuse.md)；[16 共享登录与同一目标的执行协调](16-shared-login-and-target-coordination.md)。

两项修复共享唯一记录权威，通过独立记录进程的预期版本和事务采用候选；各自保留运行时流程数据及证据，XState 不成为另一份流程存储。Drizzle 类型检查不代替原子采用，回执丢失或过期回执仍按公开幂等契约与当前资格核对。

## Acceptance criteria

- [ ] 真实网页结构或控件变化使旧条件失效时，产品自己重新观察并提出修复，不由维护者修改选择器或手填候选。
- [x] 修复仍走相同资格与派发入口，绑定当前目标、输入及有效确认／约定；超出原目标或处理规则时请求参与。
- [x] 核对实际结果成功后保存候选、证据和适用范围，自动采用合格的新做法并简短告知用户；仅验证过的分支才标记可复用。
- [x] 应用完整退出并重开后，新任务可以使用已采用的修复版本，输入和实际结果仍正确。
- [x] A、B 从相同父版本修复时分别保留完整候选和来源，按预期父版本采用；过期候选不能覆盖先采用版本或改变正在执行的固定版本。
- [x] 候选兼容性需重新核对；需要合并时形成新候选共同验证，不自动拼接两个未经共同验证的分支，也不让用户手选技术分支。
- [x] 已有提交结果未知时先核对，不能为测试修复而重发；新的停止、人工输入或共享条件改变使旧修复资格失效。
- [x] 候选记录和采用引用在原子提交中一致，保存失败或并发冲突保留各方成果；修复历史和引用进入备份、重开及清理保护。
- [ ] 取得真实变化、并发候选、错误采用拒绝及冷复用证据，保留初次失败和修订，固定版本后再验证。

## 验证方式

通过流程候选／采用与网页执行公开入口，独立核对网站效果和新进程采用的版本。并发原子性使用可控竞争，网页修复能力使用实际观察；二者证据不相互替代。

遵循[总览中的跨事项完成约定](../README.md#跨事项完成约定)，从正式产品公开入口验证并保留独立证据；不把旧实验通过当作本项完成。真实运行沿用具体案例的有效授权与累计消耗上限，本事项的发布本身不启动新实验。

2026-11-07，已完成独立实现、自主检查和本机实包组合核对，本地提交题为 `feat: 修复网页变化并原子采用流程候选`。当前 **7/9** 条关闭，`Status` 为分诊状态，真实模型／WordPress 的变化修复与完整组合仍待验，14／15／16 前置保持。

正式流程在控件或条件变化后重新观察，模型仅提议原线性路径范围内的做法。修复保持本次输入、目标与确认，经过同一预留／派发／结果检查；共享会话未核对、停止、接管或未知提交不被修复解除。核实结果后，结果、素材处理、完整候选和采用判断同事务保存，按预期父版本采用。冲突候选完整保留，后续重新验证，不自动拼接或覆盖在途固定版本。格式 16 接续 15，保留迁移前原库及备份引用。
