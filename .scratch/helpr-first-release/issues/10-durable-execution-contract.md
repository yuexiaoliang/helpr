## Question

前提：[浏览器承载与流程执行组合](07-browser-runtime-decision.md)、[提交中断后的实际结果判定](08-result-recovery-evidence.md)、[并行执行与用户参与的状态模型](09-participation-state-model.md)。

素材经模型处理后，还需要[素材、内容预览与发布版本的关联证据](13-material-preview-binding.md)，以明确被确认内容如何与实际提交对应。

在已选择的执行组合、实际结果判定和已核对的用户参与状态之上，需要持久保存哪些事实、在哪里划分原子变化，才能同时支撑流程更新、两项并行、定时取材、错过执行处理及中断恢复？

重点区分任务、执行、定时计划、流程版本、素材处理记录、发布约定和参与请求的归属。核对同一素材用于多个平台、同一流程被两项执行同时修复、登录恢复、迟到回复、重复触发和结果已产生但本地未记账等情况。

提出记录、恢复与调度的最小 Interface 和持久化方式，并用已有实验说明保证来自哪里。沿用已确认的发布与定时规则，不把特定网站或某种表格业务固化为产品状态逻辑。

输出足以写实现规格的协议与验证要点。尚无证据支持的恢复保证应形成后续实验事项；不能靠选定存储技术就宣称恢复问题已经解决。

## Answer

2026-10-12，确定以下本机持久记录与恢复协议。沿用已确定的 macOS / Electron、Playwright 与 helpr 统一执行机制；本事项决定持久事实和行为协议，不实现产品、不冻结表结构或每个字段。

### 本机记录方式

采用**单一持久记录拥有者、一个本机 SQLite 数据库，以及独立保存的不可变素材和证据文件**。宿主、调度、任务执行和流程学习通过统一 Interface 请求状态变化，执行进程不各自改写权威记录。数据库内只做短事务，不跨越网页、模型或用户等待；这不将两个独立网页任务串行化。SQLite 的单写事务限制支持这一组织方式，不能据此推定产品协议已经正确，见[官方事务说明](https://www.sqlite.org/lang_transaction.html)。

相比每项记录各写一个 JSON 文件，SQLite 让有关联的意图、确认、派发预留、素材处理和触发记录一起提交，并可检查预期版本与唯一性。现有实验的 `atomicJSON` 已有临时文件、文件同步、重命名和目录同步，不能称为没有落盘措施；它仍不提供这些跨记录关系的事务。JSON 保留用于导出、流程交换或实验证据，不作为多个独立写入者共同修改的权威记录。

关键提交需要启用并核对相应同步保证，不把 WAL 的 `synchronous=NORMAL` 当作系统崩溃后最近提交必定保留。具体绑定、日志模式、SQLite 版本与 macOS 同步行为在有界验证中固定并核查，不在此凭偏好选定；维护和备份同时考虑日志文件。官方[同步说明](https://www.sqlite.org/pragma.html#pragma_synchronous)与[原子提交说明](https://www.sqlite.org/atomiccommit.html)提供机制与环境假设，不是本产品断电恢复已经通过的证据。

数据库事务不包含网站动作或独立文件。文件先写入受管位置并核对完整性、完成所需同步，再提交引用；失败可留下待清理的无引用文件，不能留下被当作有效输入的半个文件。已引用文件缺失或校验不符时暂停依赖它的动作，不能静默回读原路径的新内容。源在取材中被观察到变化时重新取材或请求参与；固定实际选中的内容，不宣称任意正在写入的源文件都能取得瞬时快照。保留期限、空间管理、备份及用户清理交给[确定本机交付、权限与更新约定](20-local-delivery-and-updates.md)，本事项不自动删除素材。

### 要保存的事实与归属

| 事实 | 必须保留的关系 |
| --- | --- |
| 任务与执行 | 任务目标及版本、任务组引用、发起委托／计划轮次、每次执行身份和前次关联；一次任务可有多次执行，重启不凭空产生另一份业务工作 |
| 用户意图与参与请求 | 停止、接管、未知归属暂停、等待原因、明确继续的先后关系；请求属于哪个任务和执行、针对什么内容、是否仍有效。展示状态由这些事实形成，不能只存一个“运行中”字段 |
| 素材、解析与内容 | 不可变素材版本、原来源和选择依据、解析与处理要求版本、事实来源、实际预览内容和附件。按已有版本关联证据核对，路径不作为版本身份 |
| 确认与发布约定 | 已接受回复及被确认内容／目标、约定版本及撤销情况；历史确认事实与当前可派发资格分开，不用独立“同意”标志授权任意后续内容 |
| 流程及采用依据 | 固定版本、父版本、适用条件、参数与步骤条件、结果和恢复核对规则、学习／修复来源、实际验证范围、当前可复用版本引用 |
| 网页和动作事实 | 网站及登录上下文引用、宿主登记页面身份、可重新定位的目标记录、动作身份与派发阶段、已核对检查点；上传、草稿保存、最终提交分别记录 |
| 观察和结果 | 动作返回、页面后条件、实际产出核对和网络覆盖分别保存，附观察时机和依据；未知和失败不抹掉已经发生的效果 |
| 计划与素材处理记录 | 时间／时区及错过规则、取材与发布约定版本、预定轮次身份及处理决定；素材在对应约定、目标、日期／期次等工作含义下的选用、待办、未知和完成事实 |

素材与确认关系来自[验证素材、内容预览与发布版本的关联](13-material-preview-binding.md#answer)；目标和派发事实来自[验证提交中断后的实际结果判定](08-result-recovery-evidence.md#answer)。所列表达必要信息，不要求每行成为一个表或一个 Module。

截图等辅助证据保存失败不覆盖已经成立的功能核对结论，也不因此重复网页操作；必须如实记录缺失。若缺的是认定结果所必需的证据，则保持未知，不能为了继续而降低结果条件。

### 统一 Interface 与本地原子变化

持久记录 Module 对调用方提供少量行为入口：读取当前事实；提交带预期版本的意图／参与回复；领取或交还执行与资源资格；预留动作和登记观察／结果；领取计划轮次及素材工作；保存与采用流程候选。这里描述 Interface，不预定方法名或拆分进程。同一请求身份和同一输入的重复调用返回已有结论，不能再次产生业务效果；同一身份换了输入则拒绝。版本过时返回冲突和最新事实，由调用方重新核对，不能盲重试旧决定。

| 同一次数据库提交中必须一致的变化 | 浏览器或模型在事务外做什么 |
| --- | --- |
| 接受用户指令／回复、更新意图或内容授权依据、使相应旧资格与请求失效 | 停止需立即关闭派发入口并取消／终止本执行的操作进程；继续和确认只使任务具备重新核对或排队条件 |
| 领取唯一有效的执行资格、分配新执行代次、核对所需共享资源及容量 | 重新绑定和核对现场；旧工作者不能凭旧身份继续派发或覆盖新事实 |
| 校验当前身份、页面关联、输入、确认／约定、流程版本及资源资格，登记一次动作的派发预留 | 提交成功后才向网页派发；同一预留不能因通信重试再次使用。派发前还须检查进程内最新停止和输入接管信号 |
| 保存已核实结果，同时更新相应素材处理记录与本次工作进度 | 可以在事务外继续只读核对；没有核实结果时保留待核对，不将素材释放成“从未处理” |
| 领取计划轮次、记下取材或等待决定、建立本轮任务与素材工作关联 | 打开不抢焦点的标签页，按容量安排执行；重复定时通知返回同一轮次 |
| 保存完整候选及证据引用，并按预期父版本更新可复用版本引用 | 后续执行再使用新版本；候选验证或重新校准均通过受控执行入口 |

确认回复只接受一次；确认已接受后、动作尚未派发时崩溃，应恢复这份确认事实，不能把它丢掉而要求用户重复批准。停止会使旧派发资格和未完成的旧参与请求失效；用户明确继续时，核对原先已确认内容和约定是否仍适用，再建立新的执行资格。旧回调本身永不重新生效。内容或目标改变后，重新核对有效确认或发布约定；既有授权不再适用时取得新的确认，不能沿用对旧内容的单次确认，仍符合有效发布约定的新内容可以自动处理。

停止与自动动作冲突时，优先阻止新派发，再保存意图。若保存失败，保持本次禁止派发并说明记录未可靠保存，不能假装已持久停止；记录系统恢复前不运行依赖它的自动工作。若主进程也随即崩溃，尚未成功持久保存的输入不能宣称跨重启必然保留，这个窗口须在验证和界面反馈中如实处理。

### 中断、继续与结果不明

业务任务和已经选中的素材工作保持身份；每次重新取得操作资格使用新的内部执行身份，关联前次执行和核对结果，不复活旧执行。自动恢复和用户明确继续都先读取最新意图，领取恢复资格并重新核对；核对期间的新停止或改动使旧恢复资格失效。

记录拥有者启动后，先确认唯一的活动拥有者，隔离旧执行资格，并确认相关旧工作者已退出或无法再控制目标，再恢复写操作。不能仅凭等待超时、进程号变化或记录锁失效，推定旧浏览器命令和远端请求已经停止。无法确认的目标保持等待核对；已经发送的请求仍可能在旧进程退出后完成。

动作先记下可能派发，再真正发送，因此保存与发送之间一定存在空隙。恢复按实际证据分为：

- 已唯一关联的目标和实际产出满足结果规则：记录已完成，不重发，即使先前没有本地成功标志。
- 有可信的未派发检查点，旧操作来源已失效，网页、输入和授权仍吻合：仅续做尚未发生的步骤。
- 已预留或可能派发而效果无法确认，或者目标关联不唯一、文件／内容不符：保留未知，只做可独立确认的只读核对；需要时提出参与请求。网页暂时显示草稿、未找到结果、动作超时，都不是重发依据。

“继续”不会把未知变成未执行；已收到的提交和上传无法通过数据库回滚。准备中取得稳定目标身份就及时保存，不能只在整段准备成功后保存；没有保存前发生的效果仍可能不可归属。网页中的目标身份和核对规则必须由实际流程形成，不将测试代理里的请求知识或维护者填写的位置当成产品能力。

原先自动执行的工作按上述规则尽量恢复；已停止、接管、未知输入暂停和待参与的工作保持相应意图。未知输入暂停不等于用户停止两项，明确继续只针对对应任务。实际效果与用户意图独立保存，停止后核实已完成也不产生新派发。

### 流程同时修复与采用

执行固定所用版本。A、B 同时从同一旧版修复时，各自留下完整候选和验证来源；先符合采用条件的候选可有条件地更新可复用版本，另一候选保留但不能覆盖新版本。已有执行的步骤不被该更新突然改写。

另一候选与新版本兼容时，系统重新核对其适用条件和证据后采用；需要合并或重做修复时形成另一个候选并重新验证，不自动拼接两份未经共同验证的流程。保留候选不等于已能复用，也不能为了证明候选成功而重发一个结果不明的任务。网页差异若只是不同适用条件，保留有依据的分别适用关系；涉及目标或发布约定变化时沿用既有用户参与规则，不让用户手选技术分支。

此约定兑现“记住成功修复、不丢失另一项的新做法、不中途改写正在执行的流程”，现有[单流程重放](05-runtime-flow-replay.md#answer)和[条件与修复证据](14-workflow-reliability-contract.md#answer)尚未验证并发采用，必须补有界核对。

### 定时轮次、取材与已处理

按本轮用户确认，处理归属来自**取材／发布约定、目标、素材版本及该工作所需的日期／期次等含义**，不能仅用全局文件摘要去重。只改名或移动且仍在约定范围内、工作含义未变，不再自动发布到已核实完成的目标；另一平台独立记录。明确的再次发布是新的工作意图，不被历史完成记录阻止。文件内容变化形成另一素材版本；是否纳入下一轮、更新旧记录还是另发，仍由取材和发布约定决定，不能由文件监控擅自决定。

正在执行、等待、停止或结果不明的同一份工作保留原任务及素材处理记录；后续定时触发指向已有工作，不另建重复执行。新合格素材在既有约定、容量和资源允许时继续。确实失败且能确认未产生效果的重试也关联原工作；是否自动重试依现有授权、故障与恢复条件，不把所有失败都当作重新取材。

计划触发去重与素材工作去重分开：同一计划的同一预定轮次只领取一次，停止、重启和重复通知不产生另一轮；不同轮次也不能重复领取尚未完成的同一素材工作。计划修改保留版本及生效范围，不通过换版本绕过已发生轮次。时间规则应包含时区及歧义时刻的处理，创建／修改时用具体时间复述；无法唯一确定时澄清，不能依赖机器时区悄悄改变已约定时间。

错过执行仍逐计划采用已约定的“补最近一次／跳过／先问我”，没有约定不能设置全局默认。此前已经开始或等待的工作，与根本没有启动的错过轮次分别处理；补最近一次不能抹掉旧任务、清除停止或把内容确认视为过期即自动批准。计划修改、撤销发布约定、目标变化时重新核对受影响的待派发工作；已提交效果只核对，不自动撤回、改写或重新发布。

共享登录问题保存其实际影响范围，并为相关任务复用处理入口；登录恢复只解除这项阻碍，分别重核其余条件，不消除停止与内容确认。资源关系来自实际上下文和运行时流程；未知冲突时相关任务等待，任务组和同名文件均不构成共享效果的证明。

### 证据缺口与后续验证

本轮只进行已有证据和官方机制核对，没有新运行、模型调用或后台写入。已有实验分别支持结果重新核对、有限草稿续跑、输入版本关联和运行内新停止优先；不证明以上事务、单一拥有者、并发恢复与候选采用协议已经成立。

已形成两项有界前置验证：[验证持久记录与执行资格的中断一致性](22-durable-record-consistency.md)覆盖各原子变化前后中断、重复触发／回复、并发恢复与修复、旧工作者迟到、文件引用缺失及保存失败；[验证恢复核对依据的自动形成](23-autonomous-recovery-evidence.md)核对系统能从真实学习过程保存稳定目标、检查点和结果／恢复规则，避免依赖维护者事后填入位置。前者先用独立可计数的本机效果验证，不能冒充真实网页结果；后者复用独立测试后台但另定模型、上传、发布和失败重跑预算。未达到的保证如实记录，再决定是否需要修正本协议。

断电、磁盘故障、真实休眠和升级需区分：进程强杀不能替代断电证据，文档中的同步机制也不等于目标 Mac 已通过。需要改变用户机器运行状态的验证由交付和验收安排具体化；不把这一事项扩大为现在实现整套产品。

存储取舍记入 [ADR-0004](../../../docs/adr/0004-local-durable-records.md)。本次使[确定本机交付、权限与更新约定](20-local-delivery-and-updates.md)可继续；[确定首版组合验证与验收安排](21-integrated-validation-and-acceptance.md)增加上述两项验证作为前置，避免把设计决定当作已有运行保证。
