## Question

前提：[确认现有模型 API 的接入条件](03-model-api-access.md)和 [验证参数化流程的冷启动重放与修复更新](05-runtime-flow-replay.md)。

2026-10-10，用户指出探路与复用是产品的重中之重，要求更严谨可靠的设计。现有实验已证明已知参数下的动作序列能跨进程重放，但参数槽位由实验预先定义，参数化依靠字符串替换，最终结果由测试代码核对。学到一条成功路径，尚不足以证明系统学到了完整、适用范围明确的流程。

下一步需要取得哪些证据，才能选择首版的流程表示和执行机制？用一个最小候选约定及针对性实验，检验以下保证；这不是提前实现生产流程引擎，也不以确定 JSON 字段或选定某个工具代替回答问题。

### 候选设计需要回答的问题

1. **何时可以复用**：系统如何从任务目标、素材和当前网页判断某个流程是否适用？候选流程匹配之后，仍须单独核对本次发布约定；懂得操作一个栏目，不等于获得向其他栏目发布的授权。演示适用与不适用的输入，不能仅凭自然语言相似度选择流程。
2. **探路如何形成流程**：从目标、实际观察、动作及结果提取候选流程，区分具体样本值、参数引用和固定规则。参数应能表达类型、来源和约束，避免把碰巧相同的文字错误替换。步骤应说明执行前需要满足什么、完成后应观察到什么；只保存成功点击记录不够。运行时生成的步骤条件也需要检验，不能因 AI 写出了条件就视为可信。
3. **谁约束执行**：首次探路、稳定复用和修复都通过同一个执行 Module 的 Interface。AI 提议动作和修复，通用程序检查参数、页面归属、停止状态、已确认内容及允许的操作范围，并检查观察结果；这些保证不能只写在提示词中。Interface 应明确正常完成、条件不成立、结果不确定和需要用户参与的区别，复杂性留在 Implementation 内。
4. **失败后允许做什么**：等待和重试由动作效果与已观察事实决定。上传框仍可见，不证明上传完成；提交返回超时，也不证明没有提交。修复不能通过改目标、改用户已确认内容或放宽成功条件把失败变成“成功”。超出证据支持的情况应重新观察或提出参与请求；程序判断不清楚时可以按需调用 AI，但不能将猜测记成已核实的事实。
5. **何时记住新做法**：学习或修复先形成候选版本，核对实际结果后，按已有产品约定自动保存可复用版本，保留来源与适用条件。一次成功只覆盖实际验证的路径；条件分支不能凭想象扩展。执行固定所用版本，失败的候选不覆盖已有版本。具体保存原子性与并发更新规则由后续持久化事项确定。

网站步骤、字段含义和成功条件应来自运行时任务与网页事实；产品源码提供表达、执行和检查它们的通用能力。实验可以保留独立、人工定义的结果断言来判定学得规则是否正确，但不能把这些断言偷偷当作产品已经具备的识别能力。现阶段不预设完整工作流语言；只有反例表明确有需要时，才引入必要的分支或重试表达。

### 最小验证与完成条件

在已有真实后台路径上，通过候选执行 Interface 验证正常复用及下列反例，保留实际观察、动作、规则来源和结果：

- 更换素材与输入；加入不适用的流程候选及碰巧与参数相同的固定文字，验证选择与绑定不会误用。
- 延迟附件上传、出现同名控件、让控件仍然可操作但实际含义或目标改变，验证步骤条件能发现问题，而不是只检查动作是否报错。
- 让模型提出超出原目标的修复，或提议削弱成功条件，验证程序拒绝越界变更；在原约定内修复控件定位并核对实际结果后，可以保存新版。
- 区分“正确自动完成”“正确发现不适用或需要参与”“错误宣告成功”，核对真实产出。报告重复运行与失败情况，不能用一次成功声称普遍可靠。

输出候选约定、运行证据、仍无法程序化判定的部分，以及对最终流程表示和执行机制的影响。尚未验证的保证明确保留为待验证；本事项不宣称完成自然语言任务泛化、所有分支或首版整体验收。
