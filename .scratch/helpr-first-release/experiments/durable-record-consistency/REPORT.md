# 持久记录与执行资格实验报告

2026-10-12，完成[计划](PLAN.md)中的六轮预算。选定候选在最后一轮通过 39 项主验证，并完成 20 次启动争用对照。结果支持继续采用统一持久记录、条件事务与失效执行资格的路线；不是完整产品、真实网站或断电恢复已经通过。

## 结论与两处修订

1. **容量也须在领取事务中检查。** 初始候选防止了同一任务重复领取，却允许三项不同任务同时取得资格。运行 3 的第三项容量检查真实失败，见[结果](artifacts/run-3/results.json)及[当时事实](artifacts/run-3/17-third-qualification-waits-for-capacity/state.json)。将两项上限并入领取事务后，第三项等待，停止一项才可领取；没有更改首版两项并行范围。
2. **拥有权竞争要区分短暂争用与永久占用。** 运行 4 全部通过后，同源码的运行 5 出现两个冷启动进程都未就绪，见[结果](artifacts/run-5/results.json)。补充错误阶段与 SQLite 返回值后，无等待对照 10 次中有 1 次双方均得到 `SQLITE_BUSY`，均发生在拥有权锁阶段，见[直接证据](artifacts/run-6/42-startup-lock-0ms-2/lock-probe.json)。改为至多 250 ms 的锁等待后，10 次均恰好一个拥有者；另一进程拒绝进入业务记录。对照支持“瞬时锁争用、无等待立即退出”的解释，不把 10 次通过说成任意压力下都不会启动失败。等待有上限，拿不到资格不能擅自接管或删除锁文件。

容量修订落实既有协议；锁等待是本机候选的技术细节，不改变任务意图或业务工作身份。SQLite 本身的事务不会自动补齐这些执行规则。

## 核对方式与实际支持范围

调用方通过记录拥有者同一个 IPC 命令 Interface 操作，多个竞争者使用独立进程。候选只在本机数据上做短事务，网络等待在事务外。独立接收端逐次保存“收到”与“完成”，不读取候选数据库、不按动作 ID 去重；因此候选多发一次会在账本中直接出现。

| 要回答的问题 | 最终观察 |
| --- | --- |
| 确认已接受但回复丢失 | 提交前中断不留下部分确认；提交后中断保留确认及请求处理结果。重开、重复回复和有效确认后的停止／继续不增加确认或派发次数 |
| 计划轮次和素材工作 | 同一轮次只对应同一任务；后续轮次遇到等待、停止、未知或完成的同一工作仍指向原任务。只改变夹具的来源路径、模拟改名／移动时不重复领取；目标、期次、素材版本、其它约定及明确再发分别成立 |
| 预留与发送的空隙 | 预留未提交时，旧进程退出且资格失效后可以建立新执行；预留已保存但接收端没有结果时保持未知。发送资格已消费而尚未发送也不自动再发 |
| 效果已经发生、本地尚未记账 | 新进程依据独立接收端的唯一关联结果登记完成，收到次数保持 1。提交结果前／后中断，结果、动作阶段和素材工作完成事实一起回退或一起成立 |
| 旧进程、旧资格与新停止 | 拥有者竞争最多一个成功；两个恢复调用只产生一份资格。重启后的旧资格不能预留动作；核对期间的新停止使旧核对提交失效，重新只读核对仍保留停止意图 |
| 接管、未知归属及逐项继续 | 重开后保持各自意图；继续 A 不清除 B 的停止。旧待答请求和旧内容确认不能激活新工作；历史中已接受的有效确认仍保留 |
| 两项实际交叠 | A、B 的请求都到达接收端后才释放完成；数据库不跨网络等待持锁。停止 A 拒绝其新动作，B 继续；已经接收的 A 效果仍可完成并被核对 |
| 拥有者死亡后的迟到效果 | 接收端先收到请求，拥有者随后被强杀；新拥有者开始时保持未知。接收端完成后只记账，未再次派发 |
| 并发流程候选 | 两项执行固定旧版，两个候选都保存；竞争采用只更新一次当前引用，另一候选不丢失，已经存在的执行不会中途换步骤。采用前后中断不产生半份引用 |
| 不可变素材与引用 | 文件同步完成、登记前中断留下无引用文件；缺失或内容不符的已引用文件阻止预留，不回读其它内容替换。文件路径被受控阻断时不建立引用 |
| 关键保存失败 | `query_only` 产生真正的只读写入错误，`max_page_count` 产生真正的 `SQLITE_FULL`；本次拥有者停止依赖保存的派发，不留下部分候选或确认 |
| 辅助与必要证据 | 辅助文件写入失败不抹掉已核对完成；关键结果证据被隐藏时保持未知。重复效果负例收到并完成两次，候选拒绝将其认定为唯一完成结果 |

完整逐项断言与结果见[运行 6 结果](artifacts/run-6/results.json)。每项保留命令摘要、公开事实快照、数据库、进程日志及 `effects.jsonl`。只读核对程序 [verify.mjs](verify.mjs)另外检查源文件摘要、预算、全部已记录失败，以及完成事实能否与独立账本逐一对应；不为验证报告再次消耗实验额度。

## 必须保留的未知

**成功保存意图与只在内存收到意图不同。** 停止保存失败时，本次进程确实禁止派发；随后强杀并重开，持久记录仍是原来的 `auto`，动作保持未知，见[停止保存失败记录](artifacts/run-6/36-stop-save-failure-memory-gate/state.json)。不能声称未落盘的停止指令跨重启一定保留。界面必须如实告知保存未完成，恢复也不能凭没有成功记录重发。

**接收端模型有明确限制。** 本轮用唯一动作身份及虚构输入进行只读核对，确认和合格流程证据由夹具显式提供。没有证明系统能自动形成真实网站的目标身份、恢复定位或成功规则，也未验证模型对新网站的理解。该缺口继续由[恢复依据自动形成](../../issues/23-autonomous-recovery-evidence.md)处理。

**本轮只限制经该入口进入的执行。** 子调用进程没有浏览器控制能力；其旧身份遭拒绝不代表真实旧 CDP 命令或任意本机进程已被隔离。并发效果来自本机接收端，不能冒充两个真实浏览器页面同时工作。[控制连接与宿主隔离](../../issues/24-private-browser-control.md)仍是前置验证。

**进程强杀不是断电或任意磁盘损坏。** SQLite 实际配置为 DELETE、EXTRA、fullfsync=1、foreign_keys=1；独立素材使用文件与目录 `fsync`，没有证明它达到 macOS `F_FULLFSYNC` 的断电保证。页数上限不是填满系统磁盘，只读配置不是拔掉存储设备。锁文件仅用于当前本机进程拥有权，不是第二份业务数据库；未验证网络文件系统、任意文件替换或权限攻击。

**依赖版本没有因此定为产品版本。** 环境实际为 Node v24.18.0 / SQLite 3.53.1，完整 source ID 和编译选项见[环境记录](artifacts/run-6/01-confirmation-dispatch-reopen/environment.json)。已核对 [3.53 分支后续修复](https://sqlite.org/src/timeline?from=version-3.53.0&to=version-3.53.4&to2=branch-3.53&y=ci)：其中包括异常 super-journal、备份与 ATTACH、损坏输入和其它功能问题。候选没有使用 ATTACH、备份、FTS、JSONB 或外来数据库，实验也不构造损坏的 journal；这不能推定所用版本没有其它缺陷。正式依赖须重新选定和核查，再在实际打包环境复验。

约定、目标、期次和选定素材由夹具提供，未验证自然语言理解或自动判断移动后的来源仍属于原取材范围。尚未覆盖完整文件取材期间的外部改写、共享网站资源、所有计划变更／时区规则、多步骤真实网页恢复、数据迁移、备份恢复或真人参与。继续沿已有交付与最终组合验收安排取得证据，不新增产品范围，也不将本实验 Module 直接当作正式产品库。
