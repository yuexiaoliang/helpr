# 提交中断与结果判定实验计划

对应 [验证提交中断后的实际结果判定](../../issues/08-result-recovery-evidence.md)。复用已保存的流程与独立 WordPress 测试后台，取得恢复判断所需事实；不实现产品调度器或自动发现恢复规则。

2026-10-11 用户已明确批准 [额度变更](AMENDMENT-PROPOSAL.md)：新执行准备上限由 6 次增至 10 次；其它上限、截止时间与累计用量不变。下方保留最初登记。

## 固定范围与预算

- 模型调用为 **0**。流程动作来自 `runtime-flow-replay` 已核对的 `workflow-v1.json`；结果条件来自 `staged-workflow-checks` 已冻结候选。输入均为虚构文章与 Excel。
- 最多 **6** 次新执行准备、**6** 次 Excel 上传、**6** 次公开发布请求；失败和程序重启不重置。新执行在固定登记文件中领取后才能打开写入页面；代理在转发上传／发布前持久化预算预留。首次真实准备起最多 **45 分钟**，最多 **4** 次执行协议修订；达到上限保留缺口，不另开目录重跑。
- 执行和恢复使用不同 Node 进程及浏览器。进程中断使用 `SIGKILL`，故障由独立代理控制。代理只能访问已登记的测试站点，认证信息不记日志。
- 功能判定和原始观察先保存，截图独立采集。保留失败记录、源代码与流程摘要。只读恢复禁止转发写请求。

## 要取得的证据

1. **提交动作派发前**：准备可重新打开的草稿，保存素材和目标关联；在写入派发标记前终止。新进程重新核对草稿，验证是否能够只继续提交，不重复上传或新建。
2. **网站已提交、浏览器没有收到回执**：代理转发真实发布请求并扣住响应，随后终止执行进程。通过重新打开列表与公开结果核对是否已完成；不得再次发布。
3. **结果已被观察、完成记录尚未写入**：终止后重新核对实际结果，不以旧内存状态或最后一步是否返回成功作判断。
4. **派发标记已保存、动作尚未发送**：留下与“可能已发送”相同的本地记录。结果未找到仍不能自动重试，记录为无法确认。
5. 前两项以两项任务同时准备、不同进度中断运行，使用相同标题和不同正文／素材，验证结果不能串用。恢复时故意给出另一项的结果作为反例。
6. 受控设置 `stopped`、`awaiting-confirmation`、`human-control` 意图并跨进程重读；重新观察事实不能把这些意图改成自动运行。这里验证持久化意图，不验证真人输入识别。
7. 对已发布结果暂时返回不可用，核对“暂时找不到”不会被误判为“没发布”；解除故障后再只读核对。材料改变、账本损坏或流程不兼容应停止判定。

## 判定与边界

恢复候选使用通用定位和条件执行，站点入口、列表搜索、记录链接及草稿检查保存在实验 JSON 约定中。列表搜索和草稿检查由本次可观察网页校准，并非模型自动学得；标题只用于查找，必须同时核对稳定记录链接、正文、栏目、素材字节与当前执行关联。

代理知道测试站点的请求格式，用于精确控制故障和独立计数；这部分不能进入恢复判定。判定进程只能读取任务记录、流程约定和网页，不读取代理的服务器成功日志。即使结果确认完成，也不声称浏览器内部运行栈、所有上传副作用或完整产品执行已恢复。
