原 8 次失败均保留在各自 `interrupted/` 中，不改为通过。A3/B3 原监督文件的上传计数为 0，是旧代理分类错误；正确累计值以带补记理由的账本为准，不改写当时输出。A4 的重新核对放在单独 `dispatch-gap/`，原失败现场和变更前记录也保留。

失败还暴露了准备阶段的记录窗口：A4 页面已保存草稿，而正常执行记录尚未保存目标地址。此次能重新定位依赖另存的失败页面观察，不能据此宣称任意准备中断都能自动恢复。上传完成、草稿保存和最终发布是不同事实，后续协议必须分别处理。

## 验证与能力边界

`npm run check` 通过 77 个源码语法检查、25 项本机测试及原有 18 项历史证据检查；`npm run test:browser` 通过 4 项原浏览器检查与 3 项新增代理检查。新增记录测试覆盖跨进程意图、缺失／损坏记录、身份／素材不匹配与版本不兼容。`verify.mjs` 核对本次预算、源快照、运行重叠、全部中断场景、15 次只读恢复及最终网页列表。

本实验没有验证机器断电下的磁盘落盘、迟到请求最终完成的时限、多个恢复者竞争、网页被外部修改、账号变更、跨网站恢复、参与请求与真实鼠标事件关联、上传副作用的完全关联或补偿，也没有验证自动学习恢复入口和稳定目标标识。记录摘要只是完整性检查，不是安全签名。

特别是 `prepared` 能够续跑，依赖本次单一执行者确实在最终提交之前留下记录；`dispatching` 不能仅因查无公开结果就重试。浏览器原运行栈没有恢复，执行器是在新环境中重读记录、核对网页并按已知流程继续。更完整的并发恢复、版本迁移和素材处理协议由后续决策收敛。
