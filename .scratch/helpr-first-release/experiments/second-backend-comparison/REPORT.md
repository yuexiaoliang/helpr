# 第二后台流程对照证据

2026-10-11。本报告只记录技术实验事实，对应[取得第二后台的流程对照证据](../../issues/11-second-backend-comparison.md)。结论与后续决定归属见该事项的 Answer。

## 结果

Drupal 上取得了七步完整流程、换输入校准和两份冻结后样本的真实发布证据。匿名浏览器分别核对了标题、正文、栏目、栏目页收录和下载字节。校准后的完整重放与两份保留样本均没有网页动作模型调用；理解新委托仍各调用一次模型。

已有程序原样换站没有通过。两次通用协议修订及一次模型结果位置校准后才完成上述路径；维护者负责诊断、修订通用程序和启动校准。因此，这支持“网站步骤与字段定位来自运行时数据”，尚不证明任意新网站都能无需修改通用代码而自动完成，也不是产品自主修复的完整验收。

## 两次通用协议修订

第一版在学习一暴露三项可复核问题：原生 `select` 的内部值是 `1`，期望文字是“Excel 验证”；快照中含冒号的可访问名称被 YAML 单引号包装，正文控件因此被简易解析器遗漏；`SELECT` 和提交型 `INPUT` 被误报为可填写。

第二版解开实际 ARIA 行的单引号包装，收紧可填写控件类型，提供原生选项观察，并新增 `selected-label` 条件。它比较真实 `selectedOptions` 的文字与动态输入，不把 Drupal 的数字选项值写入程序。[独立原语检查](artifacts/protocol-checks/results.json)验证可观察正文、控件类型、不同内部值下的正确选项，以及选错选项时拒绝；此检查只替换本地页面 DOM，没有网站写入。

学习二中，上传响应头到达后的完成快照仍未出现文件链接；稍后的真实页面已有该文件。模型在只包含导航链接的候选中误选了 `Add content item`，字节检查正确拒绝了它，但驱动没有把该异常标为“上传已执行”，又继续提出动作。

第三版等待响应完整结束，再执行已有的页面及文件核对；后置位置或字节检查出错时继承动作已执行标志并停止；每轮文件选择限制为一次；复用失败记录时只取首个失败步骤之前的成功前缀。随后上传和完整路径通过。这是同一路径的修订后证据，不等于“响应结束即可证明任意业务操作完成”：原文件哈希和后条件检查仍然必需。

冻结的通用程序仍不包含新后台字段名、按钮名或成功文案。实际 Drupal 定位仅来自模型选择的观察节点，保存在运行时候选中。两个协议修订记录在 [meta.json](artifacts/drupal/meta.json)，最终核心源码为版本三。

## 结果定位校准与冻结

学习三的结果文字规则已绑定输入，但 `finish` 动作和提交后条件留下了训练标题常量。第一次校准的实际发布成功，旧标题定位失败，程序保留 `uncertain`。

[结果位置校准](artifacts/drupal/result-position-calibration.json)只向模型提供该次真实结果页的链接候选。模型选择实际标题链接，并使用已有 `nameInput` 绑定机制关联新标题。程序先按原结果规则和独立断言核实已提交内容，之后更新候选及其派生的提交后条件；没有人工指定网站选择器，没有再次发布该委托。旧候选保存在 [校准前候选](artifacts/drupal/candidate-before-position-calibration.json)。

第二次校准用新的虚构委托完整通过后，才保存 [frozen-candidate.json](artifacts/drupal/frozen-candidate.json)。封存摘要：


[生成登记](artifacts/drupal/heldout-generation.json)保存冻结后的样本时间、委托摘要、素材摘要和候选摘要。第二次校准与全部保留样本使用同一候选，期间未修改执行协议。

## 与 WordPress 的差异

| 差异 | Drupal 中的实际处理 | 归属 |
| --- | --- | --- |
| 区块编辑器与原生字段表单 | 七步：进入新建、填标题、填正文、选栏目、上传、Save 上按 Enter、取得结果链接 | 模型形成的运行时步骤 |
| 栏目复选框与下拉框 | 动作选择 `select`；输入仍是栏目文字 | 运行时绑定；新增通用 `selected-label` 条件 |
| 正文控件可访问名称含冒号 | 原控件从 ARIA 观察中出现并被模型选中 | 通用快照解析修订 |
| 上传后的 DOM 更新时机 | 等待完整响应后观察附件链接，再核对文件字节 | 通用动作完成与后条件边界 |
| 原生附件字段与 File 区块 | 模型选中实际文件输入及上传后的链接 | 运行时位置、同一上传许可与哈希检查 |
| 发布后链接名称含任务标题 | 模型校准为动态标题绑定 | 运行时候选校准；驱动仍由维护者启动 |
| 结果页布局 | 标题、正文、栏目和下载链接均由实际页面的有限位置提议形成 | 运行时结果规则；独立 Drupal 断言只评价 |

## 尚未取得的保证

- 两站的有限路径不能证明任意后台兼容。登录失效、复杂多框架、多附件、大文件、正文格式变化、不同语言界面、移动端，以及 Drupal 上的人工接管和停止恢复均不在此次验证内。
- 栏目输入仍只用了“Excel 验证”；其它栏目在真实完整路径中的复用未验证。局部原语反例不等同于该完整场景。
- 新的选项条件仅覆盖原生单选 `select`。自定义组合框、多选、显示标签不唯一等情况不能据此推定。
- 模型在可选列表缺少正确位置时仍可能选择错误节点。文件哈希阻止了误认，但程序和提议协议仍须有明确的“未知／不能完成”出口。
- 选项条件、结果动态绑定和动作后置错误的处理暴露出执行 Interface 必须保留的语义，不能把文字填写、选择和仅已派发都压成一个“成功”。这些事实应进入执行组合及持久记录约定。
- 新后台上传请求暴露的 body 元数据为 2,642 字节，所选文件为 3,754 字节；这仍不构成请求传输完整文件字节的证明。普通写请求继续依赖当前动作窗口和就绪条件。最终结果正确不能证明所有副作用均在范围内，关联问题继续交给[网页动作、上传数据与写请求的关联边界](../../issues/18-action-request-association.md)。

## 离线检查

在本目录运行 `node verify.mjs --check`，不连接网站、不读取凭据、不调用模型。它核对版本源码、候选封存、预算、失败留存、下载哈希、保留集生成顺序、负例和最终服务端审计，并检查 [evidence-index.json](evidence-index.json) 中的全部文件摘要。[verification.json](verification.json)保存核对结果。网站未来清理临时文件或环境变化，不会改写本次已保存的证据。
