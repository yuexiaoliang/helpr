# 重复授权的最小诊断

状态：已完成一次原生最小对照，复现同一自签名规则下换版后读取被拒绝；尚未修复，也未完成 Electron 自动更新验证。

## 已有事实

2026-10-13（Asia/Shanghai），只读核对原实验专属 Keychain 项：普通信任规则同时接受旧版和当前版；另有 `ACLAuthorizationPartitionID`，保存六个不同 `cdhash:`，没有 `teamid:`。两版签名的 `TeamIdentifier` 均为 `not set`。原始数据见 [existing-keychain-access.json](artifacts/existing-keychain-access.json)。没有读取密码数据，也未修改访问规则。

用户说明尚未开通 Apple Developer Program，也没有可用证书。本机默认搜索范围有效代码签名身份为零；实验专属自签名材料仍在原实验忽略目录。正式身份不可用是当前交付条件，不假定支付、开户或配置已获授权。

## 本轮反馈检查与预算

先把问题缩成两份使用相同实验自签名证书、相同标识和相同指定要求的本机原生小程序：旧版创建且读取一份虚构值，新版从同一安装位置读取同一项。两个版本仅改变编译版本常量，记录实际代码指纹与访问结果。所有凭据操作在该诊断进程内关闭系统交互；若需要弹窗即得到拒绝，不能通过人工授权把失败改成成功。仅操作新建的 `helpr Unattended Update Probe 20261013` 项，不读取旧实验密钥或用户凭据。

用户的“继续”涵盖这项本机可逆诊断。本轮限两次编译、两次实验签名、四次原生小程序运行（创建并读旧版、读新版、旧版清理、确认项不存在），新建与清理各一个虚构 Keychain 项；自动运行不超过 15 分钟。只复用已有实验私钥进行签名，不导出用户私钥、不改证书信任或系统策略。签名需要临时加入实验专属钥匙串搜索列表时，完成或失败均恢复原列表；遇到新的系统授权或失败就保留记录并停止。

本轮不构建、安装或启动 Electron 应用，不运行自动更新；模型调用、远程业务写入和付费服务均为零。原封装实验的预算和应用保持不动。此检查只检验 Keychain 在更换代码后的访问，不能代替 Electron／Cookie／真实自动更新的组合验证。

只有实际运行检查后，才能依据结果排列并检验原因；静态资料和旧日志用于准备反馈入口。若出现相同规则下新版无需交互即读回，必须接受这个反例，不能预设分区就是旧弹窗的唯一原因。

## 后续假设与检验顺序

以下是假设排序，供下一轮改变签名身份时使用；不是补写成已经完成的修复实验。

1. **代码指纹分区限制是换版拒绝的主要条件。** 旧项保存六个 `cdhash:`；Apple Security 在普通 ACL 验证后还检查 partition，不能将指定要求相同视为充分条件。预测：真正符合 Apple 开发证书链规则的签名若得到稳定 `teamid:` 分区，同一团队的新代码应可不经新增授权读取。下一轮先检查实际证书链与分区，再做完全相同的两版原生对照；失败即保留此反例，不靠修改 ACL 获得通过。
2. **应用标识、路径或普通指定要求变化。** 本次同路径、同标识、同指定要求仍失败，削弱了这项作为本次最小失败的解释。它仍是完整 Electron 更新必须控制的变量：应用、帮助进程、实际调用方均要核对，不能只比外层 `.app`。
3. **锁定、并发或启动阶段导致暂时不可访问。** 本次单进程顺序对照中旧版即时读回、新版被拒、旧版随后能清理，证据较弱。下一轮记录锁定状态和调用时间；若同版也失败，则先排查环境，不将所有失败都归给签名。

机制依据：[Apple Security 的调用者分区分类](https://github.com/apple-oss-distributions/Security/blob/b4bd4fda62af1ebf469ee97f0112fb49363fb482/securityd/src/clientid.cpp)、[普通 ACL 后的分区验证](https://github.com/apple-oss-distributions/Security/blob/b4bd4fda62af1ebf469ee97f0112fb49363fb482/securityd/src/acls.cpp)。引用的是邻近公开版本，不能声称与本机 Security 框架逐字相同。实测是对该机制的独立支持；仍不足以逐一归因旧实验的全部弹窗。
